Access Token vs Refresh Token

Two tokens, different roles, working together to keep users secure and signed in.

Access Token

A short-lived token used to access protected APIs on behalf of a user.

Purpose

Authorize requests to protected APIs and resources.

Lifespan

Short-lived (e.g. 5–15 minutes).

Where it is stored

In memory or a secure, HttpOnly cookie.

When it is sent

Included in the Authorization header with API requests.

Revocation behavior

Expires quickly; server-side revocation requires additional mechanisms.

Working
together

Refresh Token

A long-lived credential used to obtain new access tokens when they expire.

Purpose

Get a new access token without logging in again.

Lifespan

Long-lived (e.g. days or weeks).

Where it is stored

In a secure, HttpOnly cookie or other protected storage.

When it is sent

Sent to the refresh endpoint only.

Revocation behavior

Can be revoked on logout and rotated for stronger security.

Using Tokens on Protected Requests

After login, include the access token in your requests to access protected APIs.

Browser

Your application makes a request to a protected API.

Authorization Header

Include the access token in the request header.

Authorization: Bearer <access_token>

API Gateway

Validates the token and routes the request.

Protected API

Processes the request if the token is valid.

Authorized Response

Returns the requested data.

Refresh Flow

When an access token expires, use a refresh token to get a new one.

  1. 1

    Expired Request

    The API returns 401 Unauthorized when the access token has expired.

  2. 2

    Call Refresh Endpoint

    Use your refresh token to request a new access token.

    POST /auth/refresh
  3. 3

    Verify Refresh Token

    The server validates the token and checks expiration and session state.

  4. 4

    Issue New Access Token

    A new access token is returned for subsequent requests.

Best practices

Keep tokens secure

Store tokens safely and avoid exposing them in client code.

Handle expiration

Detect 401 responses and follow the refresh flow.

Use minimal scopes

Request only the permissions your application needs.

Security Notes & Failure States

Key security principles and common failure scenarios to consider
when building with the authentication system.

Security Principles

Core practices that keep user accounts and data safe.

HTTPS Everywhere

All authentication requests are sent over HTTPS with TLS.

Password Hashing

Passwords use a strong adaptive hash such as Argon2id.

Rate Limiting

Limit login and critical endpoints to reduce abuse.

Token Rotation

Rotate refresh tokens on use to reduce replay risks.

Secure Sessions

Use Secure, HttpOnly, SameSite cookies and server-side session controls.
